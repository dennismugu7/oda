# Decisions log

Append-only. Newest at the bottom. Format: date · decision · why · consequences.

1. **2026-09-30 · Payments: buyer pays the seller's own M-Pesa directly; the seller confirms by hand.** Why: matches the seller designs, zero fees while oda is free, no licensing exposure, fastest to build. Consequence: no STK push, no automatic confirmation or refunds in v1. The data model keeps `payment_method` extensible so an aggregator (STK push) can be added in v2.
2. **2026-09-30 · No deposits in v1.** Payment options are pay-before-delivery (full amount) and/or pay-on-delivery, per shop. Deposits → v2 (easier with an aggregator).
3. **2026-09-30 · No automated WhatsApp/SMS in v1.** WhatsApp actions open the seller's own WhatsApp with a pre-written message. Buyer tracking happens via the order link; optional buyer email. Seller alerts via Android push. Automated WhatsApp (Business Platform) → v2.
4. **2026-09-30 · Seller auth is email + password + 6-digit email code only.** No social login.
5. **2026-09-30 · Shop links live at `oda.mugu-labs.com/{slug}`.** The domain is a config value; old slugs/domains must redirect forever.
6. **2026-09-30 · Order links use a random token (`/o/{token}`)**, never the sequential order number.
7. **2026-09-30 · Products have no stock counts in v1.** Status only: Available / Sold out / Hidden. Optional was-price.
8. **2026-09-30 · Seller app is Android only; light theme only.**
9. **2026-09-30 · oda is free in v1.** No commission, no subscription.
10. **2026-09-30 · Stack:** pnpm + Turborepo monorepo; Expo (React Native, TypeScript, Expo Router) for the seller app; Next.js (App Router) + Tailwind for the buyer web + admin; Supabase (Postgres, Auth, Storage, pg_cron; no Edge Functions: server logic lives in Next.js API routes so it can share TypeScript with `packages/shared`); Resend for email; Expo push (FCM); Sentry; Vercel for web hosting; EAS for Android builds. Why: one language (TypeScript) end to end, generous free tiers, well supported by Claude Code. Check before M11: Vercel's free Hobby plan is meant for non-commercial use, so production may need Vercel Pro or another host (for example Cloudflare). Keep the web app host-agnostic (no Vercel-only APIs).
11. **2026-09-30 · Environments:** local (Docker Postgres) → staging (Neon project + R2 bucket + preview web) → production.
12. **2026-09-30 · Buyer favourites are stored on the device only.**
13. **2026-09-30 · Server logic lives in Next.js API routes.** Order mutations go through `transitionOrder()`: a conditional UPDATE on the expected-from status inside a transaction (race-safe). The Expo app uses the same API.
14. **2026-09-30 · Image sizes are generated on the device** (full ~1600px + thumbnail ~400px). No paid image-transformation service.
15. **2026-09-30 · A payment claim is not money.** Cancelling a claimed order asks the seller whether the money arrived before creating a refund.
16. **2026-09-30 · Backend moved off Supabase (supersedes the Supabase parts of #10).** Why: the owner's Supabase account already uses both free project slots for live apps, and Pro isn't affordable. New stack: **Neon** Postgres (free plan, separate staging and prod projects) + **Drizzle ORM**; **Better Auth** (email + password + email OTP) inside apps/web, with its Expo integration; **Cloudflare R2** for images (presigned uploads); **GitHub Actions** for scheduled jobs and nightly `pg_dump` backups. Consequences: authorization is enforced in the server's code (one layer + tests) instead of database RLS; the seller app talks only to our API; a short cold start after 5 min idle on Neon's free plan.
17. **2026-09-30 · Database driver: `pg` (node-postgres) everywhere, with Neon's pooled connection string in deployed environments.** Why: `transitionOrder()` needs interactive transactions, which Neon's HTTP driver doesn't offer; one driver locally, in CI and on Vercel means tests exercise the production path. Migrations use the direct (unpooled) URL (`DATABASE_URL_UNPOOLED`). Consequence: API routes run on the Node runtime, not Edge.
18. **2026-09-30 · Version pins driven by Expo SDK 57:** TypeScript 6.0.x (not 7) and React 19.2.3 in both apps (React Native needs an exact match). Expo SDK 57 over 58 (still pre-release). Drizzle 0.45 (1.0 is a release candidate). ESLint 9, because `eslint-config-next`'s plugins don't support ESLint 10 yet. `@react-native/metro-config` and `react-native-worklets` are pinned via pnpm overrides to the versions SDK 57 was built against. *Amended 2026-10-01: the `react-native-worklets` override is removed; see #24.*
19. **2026-09-30 · No NativeWind.** The web uses Tailwind 4; NativeWind's stable release needs Tailwind 3. The seller app uses `StyleSheet` with `@oda/ui-tokens`. The web theme (`theme.css`) is generated from the same `tokens.ts`; named spacing tokens aren't emitted to CSS because they'd override Tailwind's `max-w-md`-style sizes, so the web uses Tailwind's numeric 4px scale.
20. **2026-09-30 · pnpm uses its default isolated `node_modules`**, including for Expo (Metro resolves it; no `nodeLinker: hoisted`). Install scripts are allowed per package in `pnpm-workspace.yaml`, and pnpm's minimum-release-age guard lists the few just-published versions we pin.
21. **2026-09-30 · Local Postgres runs on port 5442** (not 5432/5433) to avoid other Postgres instances on the dev machine.
22. **2026-09-30 · The R2 staging bucket moves from M0 to M2.** Why: nothing uses file storage until photo and logo uploads in M2, so creating the bucket and keys earlier only adds unused secrets. Consequence: the M0 staging checklist in `milestones.md` is met without R2; M2 starts by creating bucket `oda-staging` and a token scoped to it.
23. **2026-10-01 · Android builds run locally on the dev machine (Gradle), not on EAS cloud.** Why: the free EAS queue took ~1 hour per build, which is too slow for the dev loop. EAS stays configured (`eas.json` development + preview profiles, project linked) as a fallback. Consequences: the machine has 16 GB RAM and an earlier local build exhausted it, so `~/.gradle/gradle.properties` (user-level, outside the repo, because `apps/seller/android/` is regenerated) caps Gradle at 3 GB heap + 768 MB metaspace, the Kotlin daemon at 1.5 GB, 2 workers and no parallel builds; quit Docker Desktop during native builds. Dev builds compile only `arm64-v8a` (`reactNativeArchitectures`) to cut native compile work. **Release builds (M11) must also include `armeabi-v7a`**, because many budget phones in Kenya are 32-bit; set the architectures explicitly in the release build, since the user-level file would otherwise apply.
24. **2026-10-01 · Native modules come in at the Expo SDK's versions, enforced in CI.** Why: `expo-router` and `@expo/ui` declare `react-native-reanimated`, `react-native-worklets` and `react-native-gesture-handler` as `*` peers, so pnpm auto-installed the newest releases (Reanimated 4.7.0, Gesture Handler 3.3.0) instead of SDK 57's (4.5.1, ~2.32.0). Our Worklets override (#18) then forced 0.10.1, which Reanimated 4.7 rejects, so the EAS build failed in Gradle. `expo install --check` and expo-doctor only look at the app's direct dependencies, and CI builds no native code, so neither caught it. Fix: the three packages are direct dependencies of `apps/seller`, added with `npx expo install`; the Worklets override is gone. Consequence: CI runs `pnpm --filter @oda/seller deps:check` (`expo install --check` + `scripts/check-native-deps.mjs`, which fails on any installed copy, transitive included, outside SDK 57's `bundledNativeModules.json`). Add native modules with `npx expo install`, never `pnpm add`.
25. **2026-10-01 · Postgres 18 everywhere (was 17).** Why: the Neon staging project was created on 18, Neon's default for new projects; Neon's changelog (2026-05-01) states Postgres 18 is generally available and fully supported for production. Neon can't change a project's major version in place (upgrades mean a new project + data migration), so local and CI follow Neon rather than the reverse. Consequences: `docker-compose.yml` and CI use `postgres:18-alpine`; the compose volume mounts at `/var/lib/postgresql` (18+ images keep data in a versioned subdirectory there, and the old `/data` mount is refused). Existing local volumes must be rebuilt with `pnpm db:reset`. The production Neon project (M11) must also be 18.
26. **2026-10-01 · Until M11, Vercel's Production and Preview environments both use the Neon staging database (`oda-staging`).** Why: there is only one database before launch, and a separate production project would sit unused. Consequence: the Vercel Production deployment (from `main`) *is* the staging site, so treat its data as disposable. At M11, create a production Neon project (Postgres 18, #25) and change the Production-scoped `DATABASE_URL` (and later secrets) in Vercel; Preview keeps staging. Vercel project `oda`: root directory `apps/web`, files outside the root included, Node 24.x, `ENABLE_EXPERIMENTAL_COREPACK=1` so the pinned pnpm is used.
27. **2026-10-01 · Staging migrations run in GitHub Actions, not from a laptop.** Workflow `migrate-staging` runs `pnpm db:migrate` against Neon staging on every push to `main` and on manual dispatch, with the direct (unpooled) connection string from repository secret `NEON_STAGING_DATABASE_URL_UNPOOLED`. Why: the owner works partly from a phone; no Neon credentials on dev machines (replaces the planned `packages/db/.env.staging.local` + `db:migrate:staging`); every merged migration reaches staging automatically. Consequences: runs are serialized (`concurrency`, never cancelled midway); the job refuses a pooled (`-pooler`) string. GitHub only offers manual dispatch once the workflow is on `main`, so the first run is the PR #1 merge. Vercel deploys in parallel with the migration, so a deploy that needs a new migration can briefly hit the old schema; revisit (e.g. migrate before deploy) before M1's tables are used on staging. Production (M11) gets its own workflow and secret.
28. **2026-10-01 · Windows Android builds use ninja 1.12+ (long-path aware) inside the SDK's CMake 3.22.1.** Why: native modules compile inside pnpm's store, where paths reach 280 characters (e.g. `react-native-worklets/android/.cxx/…/ReactAndroidConfigVersion.cmake`). The ninja 1.10.2 bundled with SDK CMake 3.22.1 can't see paths over 260 even with Windows long paths enabled, so it looped (`build.ninja still dirty after 100 tries`). Rejected: lowering pnpm's `virtualStoreDirMaxLength` (its floor of `_` + 32-char hash only gets to 253); relocating each module's `.cxx` folder (Worklets hard-codes `${projectDir}/.cxx` in its prefab/PCH scripts); moving the repo to `C:\oda` (257, too close). Setup (once per Windows machine): `sdkmanager "cmake;3.31.6"`, then copy its `bin\ninja.exe` over `cmake\3.22.1\bin\ninja.exe` (old one kept as `ninja-1.10.2.exe`). Consequences: no repo code, no effect on CI/Linux/EAS; must be redone if the SDK's CMake 3.22.1 is reinstalled.
29. **2026-10-01 · Tighter Gradle limits (amends #23):** `-Xmx2560m` heap and `org.gradle.workers.max=1` in `~/.gradle/gradle.properties`. Why: with 3 GB and 2 workers, the release build hit critical memory pressure while compiling native modules and was stopped. Consequence: one C++ compile at a time, so native builds are slower (≈20–30 min cold). Claude Code's low-memory stop stays enabled.
30. **2026-10-01 · Kotlin compiles inside the Gradle daemon (amends #29):** `kotlin.compiler.execution.strategy=in-process` in `~/.gradle/gradle.properties`. Why: the `m0-preview-2` release build was stopped for low memory during JS bundling + Hermes compile, while a separate Kotlin compile daemon (~1.2 GB) sat idle next to the Gradle daemon (~1.5 GB). In-process removes that daemon without raising any limit (`kotlin.daemon.jvmargs` no longer applies). Consequence: Kotlin compilation shares the 2560m Gradle heap; if a build ever fails with a Gradle `OutOfMemoryError`, revisit the heap rather than re-enabling the daemon.

33. **2026-10-01 · Input rules in `packages/shared` (M1).** **M-Pesa code** (owner-approved): 10 characters `A–Z`/`0–9` starting with a letter, case-insensitive; **no digit required**, because real codes are random and about 5% are all letters. In a pasted SMS, the token right before "Confirmed" wins, otherwise the first match. Why: a false accept is harmless (the seller confirms by hand), a false reject blocks a paying buyer. **Slugs:** spec rules (`a-z0-9-`, 3–30, reserved list) plus no leading, trailing or double hyphens; names are slugified with accents folded and `&` → "and". **Phones:** Kenyan mobiles only (`+2547…` / `+2541…`), input with `07…`, `01…`, `7…`, `1…`, `254…`, `+254…` and spaces/dashes/dots/brackets. **Quantities:** 1–99 per line.
34. **2026-10-01 · M1 schema refinements to `data-model.md`** (migrations `0001_schema`, `0002_triggers`). (a) **Better Auth tables are `auth_user`, `auth_session`, `auth_account`, `auth_verification`** with uuid ids (`user` is reserved in Postgres; owner-approved); `profiles.id` references `auth_user.id`. A missing profile is created on first use (idempotent). (b) **`orders.awaiting_payment_since`**: set when an order (re-)enters `awaiting_payment`; the 48h auto-expire counts from it, so "payment not found" gives the buyer a fresh 48h (owner-approved). (c) Primary keys the doc left implicit: `review_items (review_id, order_item_id)`, `shop_visits_daily (shop_id, day, source)`, `rate_limits (key, window_start)`, `order_events.id`. `review_items.rating` is nullable (an item can be left unrated). (d) **`shops.owner_id` is unique** (one shop per seller, v1). (e) **Database guards:** a trigger rejects any UPDATE of `orders.status`/`payment_status` unless the transaction set `oda.transition = 'on'`, which only `transitionOrder()` does; slug triggers move old slugs to `shop_slug_history` automatically, let the owner reclaim their own, and refuse another shop's live or historical slug. (f) **Same-shop composite foreign keys:** products→categories, orders→delivery areas, payment claims/reviews/notifications→orders, notifications→reviews all reference `(id, shop_id)`, so a row can never point at another shop's data (deleting a category/area sets only the reference to null). (g) Aggregates by trigger: `units_sold` (sale statuses, incl. orders created as a sale), `delivered_count`, shop and product ratings (product ratings ignore unrated items). (h) Product search: GIN expression index with the `simple` text-search config (mixed English/Swahili). (i) `rate_limit_hit(key, window_seconds, max)` fixed-window SQL function. (j) Checks: pay-before or pay-on-delivery on; one active payment account; paybill reference rules; was-price > price; `total = subtotal + delivery_fee`; qty 1–99; ratings 1–5; pickup orders have no delivery area; onboarding step 3–6. Changing the triggers or foreign keys means a new hand-written migration (drizzle-kit doesn't track them).
